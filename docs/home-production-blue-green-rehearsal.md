## Run the loopback rehearsal

Use Python 3.9+ and native [Caddy 2.11.4](https://github.com/caddyserver/caddy/releases/tag/v2.11.4), the version in Home Compose.

```sh
python3 scripts/infra/home-production/rehearse-blue-green.py --caddy /path/to/caddy
```

The fixture renders the existing inner gateway routes for two loopback app/API pairs and a loopback-only admin port. It probes app, API, `/llms.txt` and the internal-route denial continuously. Each run rejects an invalid reload, switches to green, drains and retires blue, then brings blue back and reverses the switch. The reported switch time includes the reload command and the four route checks. Held requests finished on their original upstream after the reload returned. The runs used synthetic backends over HTTP/1.1. The Keep host edge, real app and API, database, TLS and upgraded streams need separate proof.

The fixture checks the adapted JSON before starting or reloading Caddy. The guard rejected wildcard ingress, wildcard admin, extra listeners, automatic HTTPS and an extra Caddy app. An independent socket inspection observed only `127.0.0.1` listeners. All eight ports observed in the normal run, and all four observed in each of the SIGTERM and injected-failure runs, refused connections after exit.

The [offline journal fixture](../scripts/infra/home-production/atlas-deploy-journal.py) uses an explicitly initialized SQLite journal and the same exclusive, nonblocking `flock` semantics as Keep. It commits the claim before launch, passes the locked file descriptor to the command, and commits success after the full deploy and smoke command returns and before acknowledging it. The lock path must retain its inode. A missing or corrupt journal blocks execution. [SQLite durability settings](https://www.sqlite.org/pragma.html#pragma_synchronous)

An unresolved claim fences all later attempts, including new workflow runs and different releases. Reconciliation under the shared lock requires evidence tied to the exact attempt, source SHA and image ID. Definitive outcomes are completed deploy and smoke, proven never invoked, or verified recovery to a safe prior state. A failed command, checkout HEAD or a mutable image tag cannot settle a claim. A recovered or never-invoked tuple stays closed. A new invocation requires fresh authorization. A later attempt of the same successful run commits its exact identity and binding as a reference to the original receipt before returning. If its reply is lost, read-only reconciliation of that exact attempt returns the historical receipt after the run ends. The receipt does not assert which release is live now.

## Switch and rollback sequence

1. Under the existing production/backup interlock, record the active color, previous digest, candidate digest and recovery inputs. Verify the exact candidate and pull it. Keep candidate runtime configuration and credential admission tied to that digest.
2. Apply forward migrations while blue is serving. Use expand/contract. Keep the old release's read and write contracts valid through the rollback window, and defer destructive contraction until rollback no longer depends on the old schema. Exercise old writes during migration and time DDL lock waits separately. Include rows with newly introduced status values when checking old readers, since even an additive enum change can affect rollback. [Jobs migration example](../packages/db/prisma/migrations/20261115020000_jobs_lifecycle/migration.sql)
3. Start green app/API with color-specific networking, including the web image's build-time `api:3001` alias. Keep schedulers and workers single-owner. The API currently starts background work when it starts, so give standby startup an explicit way to defer that work. Probe both unpublished candidate endpoints every second, including an application read through the candidate API to the migrated database. Verify their revision and atomically switch the app, API and loopback Jobs lane. Keep the host edge's existing Owner, webhook and Jobs restrictions. Its direct `127.0.0.1:3001` Jobs upstream currently bypasses the app gateway.
4. Smoke the externally served revision and keep blue alive while admitted requests drain. Cover browser assets across a release boundary, webhook intake, Jobs calls, SSE, uploads and range responses with the pinned releases. Caddy defaults to closing WebSockets at reload. Any upgraded connections that need continuity require an explicit stream policy and test. Retire blue after drain and retain the prior digest, configuration and backup proof through the rollback window. Backups must resolve the active pair and must avoid ambiguous slots. Prune afterward, keeping rollback and backup references. [Caddy stream behavior](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#streaming)
5. Before switch, a failed migration, health check or reload leaves blue routed. Reconcile migration state before retrying. After switch, use a protected GitHub Actions rollback to an explicitly selected, previously admitted digest, with its compatible configuration and the same lock. The rollback request must keep the control workflow at current `main` and validate the prior release separately. Bring the prior pair up if needed, check it on the migrated DB, reload and drain the failed color. Leave forward migrations and new writes in place. Exercise old → new writes → old reads and writes in Docker and compare counts and hashes. An incompatible schema requires a separate recovery decision and paired data reconciliation.

Measure command start → first externally observed candidate revision, with continuous requests and no client retries. For just-pushed runs also record the push timestamp. Record queue and wake-to-runner-ready time, build, verification, release admission, registry transfer, migration, readiness, route switch, and drain separately. Include old-to-new and new-to-old samples and any 5xx, timeout, reset or partial stream. The 40 s prebuilt and 120 s immediate-push targets remain open.
