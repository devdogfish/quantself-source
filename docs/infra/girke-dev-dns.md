# girke.dev DNS changes

[ADR 0045](../adr/0045-self-hosted-home-infrastructure.md) governs the provider decision. Keep Spaceship registration, its two authoritative nameservers and DNSSEC. Keep the staged Cloudflare zone inactive and Vercel direct. A change to those decisions requires explicit Owner approval and an ADR amendment. Follow the [infrastructure workflow](../agents/infrastructure-sessions.md) for live work.

Cloudflare’s nameserver warning refers to its pending setup. Spaceship remains the live DNS provider, so the warning requires no action while this policy applies. Cloudflare expires pending Free zones after 28 days. [Cloudflare zone status](https://developers.cloudflare.com/dns/zone-setups/reference/domain-status/)

## Classify service hostnames

Maintain one private inventory alongside the protected baseline. Give each service hostname an **internal** or **public** classification. Record the service and access path in the private change ledger when adding or moving it. Include legacy and rollback records until they are removed. For DNS review, classify the route the record actually points to and record any separate access fence.

| Class | Expected DNS and access |
| --- | --- |
| Internal | Resolve to Tailscale addresses and gate the listener through tailnet policy. Verify reachability from approved clients and denial from unauthorized clients. The production dashboard follows this path. |
| Public | Use the reviewed internet-facing edge. Vercel serves the apex, demos and redirect hosts. Gate uses its Tailscale Funnel hostname for the allowlisted public webhooks. A public DNS target can still have an application fence. The legacy Hostinger dashboard is a fenced rollback endpoint with a public DNS target. [Cutover evidence](https://github.com/devdogfish/quantself/issues/209) |

Keep new internal names and addresses out of Git, tickets, logs and public resolvers. Keep complete zone exports in the protected baseline storage. Publishing an internal A or AAAA record in the public zone exposes the name even if the listener is tailnet-only. A per-host public TLS certificate also exposes its name through Certificate Transparency. For a new internal name or a certificate-scope change, propose a DNS-01 wildcard certificate to avoid per-host CT entries, split DNS to keep labels out of public DNS, or both. Get the Owner's decision before implementing either change or publishing a new internal name. Keep the existing dashboard DNS-01 issuance and renewal until the Owner approves a replacement. [Certificate Transparency](https://letsencrypt.org/docs/ct-logs/)

Host redirects on subdomains of an existing domain through Vercel. Keep distinct domain roles and reuse the portfolio's [existing redirect routing](../website-analytics.md) where it applies. [ADR 0049](../adr/0049-domains-and-agent-email.md)

## Verify a DNS change

1. Run `bun run dns:girke check`. It checks registration and delegation against registry RDAP, validates that Google's DS matches the registry, compares signed apex answers from Google and Cloudflare, and checks the Vercel HTTPS response. Save the DS fingerprint in the private change ledger. Verify current portfolio and mail routing, including MX, SPF, DKIM and DMARC where configured. Resolve any failure before applying the plan.
2. Capture a complete **before** snapshot in protected storage outside the repo. Use Spaceship Advanced DNS or the read-only [Spaceship resource-records endpoint](https://docs.spaceship.dev/#tag/DNS-records). For API reads, prefer scoped read credentials through the private handoff. Start at `skip=0` with `take=500`. Advance `skip` by the number of returned items until all `total` records are gathered. Keep the API's `{items, total}` shape with combined items. Restrict local files to the Owner. Retrieve the latest accepted **baseline** and confirm continuity with the [#209 historical baseline](../home-production-cutover.md#admission) and later approved changes. Reconcile unexplained differences before proceeding. Keep snapshots, auth codes and credentials outside Git.
3. Prepare an **expected** snapshot containing only the reviewed edits to the before snapshot. Pass the private classification file as JSON with `before` and `after` objects mapping zone-relative names to `internal` or `public`. Include every service owner name with an address or alias record in each view. Run `bun run dns:girke plan BASELINE BEFORE EXPECTED INVENTORY`. This rejects baseline drift, missing classifications, misclassified address records and changes to protected portfolio, mail, CAA or delegation records. Mail migration is tracked separately in [#278](https://github.com/devdogfish/quantself/issues/278).
4. Apply only the separately authorized record edits in Spaceship. Capture a fresh **after** snapshot and run `bun run dns:girke compare BASELINE BEFORE EXPECTED INVENTORY AFTER`. Retain the record count and digest. Run `bun run dns:girke check` again and require the same DS fingerprint. Query both Spaceship authorities for the changed RRsets and verify the expected answers. Verify production HTTPS and mail routing, including MX, SPF, DKIM and DMARC where configured. Verify the affected private access or public delivery path, and confirm temporary DNS-01 records clear after issuance.
5. Record the authorized changes, counts, fingerprints, DNS and service checks and the before/after private snapshot references in the change ledger. Promote the verified after snapshot to the next baseline. For a mismatch, reconcile the actual provider state and use the recorded before snapshot for the scoped rollback. Never retry a write on the strength of a timeout alone.
