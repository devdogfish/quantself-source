# Consumer cloud targets for offsite Quantself backup

**Research date:** 2026-11-13. Prices and product support are time-sensitive; recheck vendor checkout and quotas before purchase. Canadian prices shown when official pages exposed them. USD/EUR prices are explicitly labeled and may vary by billing country, tax, promotion, and account.

## Decision summary

For a Debian home VM running nightly archives, shortlist:

1. **Existing Proton Drive** if the already-paid account has enough unused quota and the desired backup shape can be uploaded by its official CLI. It now supports scripted Linux uploads with Proton E2EE, but Proton is not a restic backend: rclone's Proton connector is beta and uses an undocumented API. For a deduplicated restic repository, the more supportable options are Filen/Koofr/Google/pCloud; using Proton entails either discrete encrypted dated artifacts or accepting the beta connector.
2. **Koofr** for low-cost Linux upload through vendor-supported WebDAV or rclone; its smaller paid tiers are billed yearly. Its separately available Koofr Vault is client-side encrypted, but general storage isn't E2EE; simplest is encrypting the archive before upload.
3. **Filen** adds a serious free encrypted alternative: 10 GB free where eligible, official Linux CLI with upload/stateless operations, and a current rclone backend. Its new Rust CLI sync integration is still moving through beta, so pin/check which CLI workflow is being used.
4. **Google One** for a mature API ecosystem; use `rclone` with the official Google Drive API. Free 15 GB is shared with Gmail and Photos. Canadian App Store listing prices are included below; verify Google account checkout.
5. **pCloud** is particularly suited to recurring unattended transfer: pCloud officially documents rsync/SSH as the recommended protocol for large recurring server/NAS backups. Use archive-side encryption; pCloud's Crypto folder cannot be reached through WebDAV/rsync. Linux desktop exists, but is not necessary for rsync.

The current source set is about **3 GB**. Treat **10 GB as a stored-repository budget scenario**, not source size. No backup repository has been built yet, so retained storage cannot be estimated from source size alone. Snapshot storage depends on backup format, change rate, deduplication, and retention. Measure the initial repository and growth before selecting capacity. Free quotas may fit the initial source, but only if unused quota also fits the *stored repository* and its retained history. No paid storage floor is assumed here.

All services below can hold a client-encrypted archive where a compatible upload path exists. In that case the service receives the ciphertext; do not infer that it can read source contents. Provider-native E2EE is a separate convenience/property from the independent backup snapshots.

## Backup method and storage planning

### Preserve backup history separately from cloud sync

A mounted/synced folder (`rclone sync`, Dropbox sync, pCloud sync, OneDrive sync) mirrors current state. A source deletion or corruption can propagate; trash/version history helps temporarily but is provider-controlled and time-limited. Use **append-by-snapshot backup semantics**: produce a DB-consistent dump and attachment archive, then add them to a repository with snapshots and retention (e.g. restic). Upload the repository to a dedicated cloud directory. Avoid a destructive mirror command for the only copy.

Restic is designed for scheduled snapshots and encrypted repositories; it supports SFTP, B2, S3, Google Cloud Storage, Azure and arbitrary rclone backends. It deduplicates common data among snapshots and has a documented retention/prune workflow. Its repository password is essential for restore. Sources: [restic backend list](https://restic.readthedocs.io/en/stable/), [backup/scheduling](https://restic.readthedocs.io/en/stable/040_backup.html), [retention/prune](https://restic.readthedocs.io/en/stable/060_forget.html), [encryption](https://restic.readthedocs.io/en/stable/070_encryption.html).

Rclone supports many consumers and a `crypt` wrapper that encrypts file contents and (by default) names locally before transfer. This can protect archive files on providers that lack native E2EE; configure a dedicated encrypted path and never upload raw archives into the underlying remote by mistake. Sources: [rclone supported providers](https://rclone.org/), [rclone crypt](https://rclone.org/crypt/).

Proton's official CLI supports scheduled uploads, but is not a restic backend. Proton's rclone backend is explicitly beta and depends on an unpublished Proton API / Proton API Bridge. The official CLI says to upload only data that changed; its public docs don't establish content-aware incremental upload, so don't assume a full archive can be uploaded every night without excess transfer. A Proton approach needs to demonstrate changed-only uploads with the chosen artifact format and restore procedure. Sources: [Proton CLI fair-use/automation docs](https://proton.me/blog/proton-drive-cli), [CLI README](https://github.com/ProtonDriveApps/sdk/blob/main/cli/README.md), [rclone Proton backend limits](https://rclone.org/protondrive/).

### Encrypted archive recovery

- Encrypt at the backup layer (restic repository encryption or rclone crypt). Keep secrets out of command arguments/logs and out of the only machine being backed up.
- Store **two independent recovery copies** of the repository password/key, offline and in distinct physical locations. Include the exact tool/version, repository URL/backend, restore commands, and any DB decryption/application secrets in a recovery note. Test a restore to a clean host at least once.
- Do not rely on the provider account password or native E2EE alone as the only recovery path. Proton, MEGA, pCloud Crypto and Koofr Vault all depend on user-held secrets; vendor E2EE cannot recover lost keys. For archive-side encryption, losing the restic/rclone key makes the ciphertext unrecoverable even if the account remains open.
- Keep a second independent copy protected from the server's normal credentials. For cloud, separate write credentials or a provider account not logged into the VM helps limit ransomware/credential compromise. For removable media, keep at a trusted offsite location, disconnect it when not backing up, and encrypt it before it leaves the home.

## Alternatives outside consumer cloud

- **Encrypted USB rotated offsite:** Low recurring cost; buy two capacity-sized drives, encrypt each locally (e.g. LUKS), and rotate one to a trusted offsite location. Strong physical separation if disconnected. Human rotation is a failure point; label/check media, keep one drive offline, and schedule restore checks. Size drives from the measured repository and retention policy, not the source size alone.
- **Friend/family server:** Offsite SFTP/SSH or restic REST repository can cost little and has no consumer quota ceiling, but availability, bandwidth, host security, and relationship continuity become dependencies. Use a dedicated least-privilege account/key, encrypted repository, server-side quota, and no delete permission if the server setup supports append-only or restricted access. Test return transfer and restore. Restic documents SFTP and REST backends; source: [restic backends](https://restic.readthedocs.io/en/stable/).

## Recommended shortlist for this setup

1. Check Proton's included storage and current unused quota. If considering it, prove browser login, post-reboot credential access, listing, upload, download/restore, permission scope, and repeated-upload behavior on the Debian service account. Public docs leave headless unlock, token scope, and incremental detection unresolved. Don't upload a whole multi-GB archive nightly; any Proton design must demonstrate changed-only transfer within Proton fair use. For deduplicated restic, its official CLI is not a backend; rclone's Proton backend is beta.
2. For supported restic/rclone snapshots, compare Filen, Koofr, Google, OneDrive, or pCloud against the **measured repository size and retention**. Their plan capacities/prices above are options, not a paid-storage recommendation. pCloud's minimum paid individual plan is 500 GB; Koofr has smaller annual tiers. Verify country VAT and billing terms before purchase.
3. Use Google One or OneDrive when ecosystem/account value outweighs tighter privacy. Configure least privilege and encrypt at source. Avoid iCloud as Linux unattended target.
4. Configure and restore-test the VM's PBS job; that service is not yet backing up this VM. Then add one logically separate offsite copy: cloud, rotated encrypted USB, or friend server. Backup completion messages alone do not prove restoreability.
