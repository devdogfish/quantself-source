# GitHub-backed to-dos and embedded voice

To-dos belong to a dedicated GitHub repository, separate from Quantself development and other software repositories. GitHub issues, organization-level issue fields, labels, native relationships, and each issue's scheduling data are authoritative; Projects and the day's calendar are rebuildable views. Quantself exposes these records through its existing authorized API and preserves the completed Web Client design. It must not create a second authoritative task or calendar database. The first release shows the dedicated to-do repository; it does not combine software-development queues with to-dos.

The production private task repository is `devdogfish-workspace/todos`; the original `devdogfish/todos` retains bootstrap documentation. The owner has created `devdogfish-workspace`; its private `todos-integration-test` repository holds isolated field checks. No existing repositories have been transferred. The private `devdogfish-todos` GitHub App (ID `5472947`, installation `175285462`) is installed on exactly the test and production to-do repositories, with Issues read/write, Metadata read, organization Issue Fields read, and organization Projects read/write. Installation-token authentication, issue-field read/write/readback, and private Project membership checks passed. The private Me Project exists; production-only token access passed. Private Jarvis authentication and temporary conversation access passed; isolated synthetic client-tool and audio-download probes passed. Real Quantself server tools and capture persistence remain implementation work. One task may have Planned Work Sessions across multiple days, with completion tracked once on the task. Scheduling another session must not duplicate the task or imply that it has been completed.

The owner's final simplification rejects a separate Daily Plan issue, file, or table. Keep each task's current priority marker, rank, and scheduling data on that issue, and derive the UI's day view from those records. Preserve multiple sessions, fixed appointments, and preparation/travel allowances. Do not implement saved proposed/approved day snapshots or a separate manual-override log. Explicit edits update the relevant task data; external agents can suggest changes in conversation. This replaces the earlier one-file-per-day proposal and removes its need for repository Contents write permission.

Embed ElevenLabs in the Web Client using a reusable capability boundary, with only to-do tools exposed in this release. Inventory and other feature integrations are outside this specification. AI interpretation and conversation remain with the external provider; durable operations use the same Quantself API authorization and validation boundary as other Clients. Phone access and the nightly call are later scope.

Store original capture audio as untouched files behind a small storage interface. An environment variable selects the storage root, so moving the archive to an HDD requires relocating the files and changing configuration, not changing stored identifiers or application code. PostgreSQL stores capture metadata only: a relative storage key, SHA-256 hash, transcript, and links to the GitHub issues produced. This archive metadata is not an authoritative task store. Retain recordings and transcripts until the owner explicitly deletes them; no automatic expiry.

The owner's latest instruction to derive planning from individual issues takes precedence over the supplied storage brief's PostgreSQL DailyPlan, Override, and RankingRecord tables and the earlier separate GitHub daily-record design. The brief's suggestion to defer appointment timing and buffers likewise does not remove the already-required calendar behavior. Its field-versus-prose principle and organization-level issue fields replace the earlier design's reliance on Project-only fields for canonical facts.

The separate to-do workflow already owns agent execution. Quantself displays proposals, approval controls, progress, blockers, and results; it does not implement the runner. In this repository's to-do integration, `ready-for-agent` is a proposal, while `agent:implement` approves execution and `agent:queued` approves waiting for prerequisites. Software-repository label meanings must not leak into this integration.

When GitHub is unavailable, already-loaded data may remain visible as stale, but edits pause until access recovers. There is no offline mutation queue. Preserve the completed UI; the owner permits rebuilding underlying integration code as needed. Verify platform setup with isolated live-service checks before handing implementation to Sandcastle, without dispatching a to-do executor or placing phone calls.

This supersedes ADR 0024's local task-data ownership and prohibition on embedded platform integration. ADR 0012's single API boundary and ADRs 0025–0026's owner-controlled priority and prerequisite-aware suggestions still apply. Integration setup and validation remain prerequisites to implementation handoff.

Platform account, permission and isolated transport checks are complete. The current [implementation handoff](https://github.com/devdogfish-workspace/todos/blob/main/docs/implementation-handoff.md) supersedes older pending-setup notes in PRD #103; real task endpoints, capture persistence and playback finalization are implementation acceptance work. The [v1 scheduling contract](https://github.com/devdogfish-workspace/todos/blob/main/docs/issue-scheduling-format.md) fixes issue-body representation and conflict behavior before implementation. Use the existing area/action authorization model with separate read, write, execution-approval and permanent-deletion capabilities for to-dos.
