# Password managers for Agents

Researched 2026-11-14 for [#214](https://github.com/devdogfish/quantself/issues/214). [ADR 0041](../adr/0041-agents-are-coworkers-outside-quantself.md) and [ADR 0046](../adr/0046-agents-own-their-tasks-and-sandcastle-is-engineering-only.md) give each Agent its own accounts, OS user and Hermes profile. [ADR 0045](../adr/0045-self-hosted-home-infrastructure.md) puts Agent services on the Owner’s machines.

A **Vaultwarden password vault** holds an Agent’s website credentials. **OpenCloud Vault** is the Owner’s private file space. [ADR 0045](../adr/0045-self-hosted-home-infrastructure.md)

## Recommendation

Use **Vaultwarden with the official Bitwarden CLI (`bw`)**. Give Sam, Stacy and Tyler separate Vaultwarden accounts and personal password vaults. Use a separate login service for unattended sign-in. The [Stacy pilot](#stacy-pilot) verified unlock after service restart and idle expiry with fake credentials. Complete the [rollout checks](#before-production-use) before adding real credentials. Give each Agent a dedicated CLI data directory and browser profile. Use an Owner-controlled organization for sharing Agent work credentials. Start with Vaultwarden 1.37.5 or a later patched release. Version 1.37.4 fixed an access-control flaw that affected revoked and unconfirmed organization members. Restrict the service to HTTPS over the home tailnet with access from the Owner and intended Agent machines. Plan updates and a restore check before relying on it. [Vaultwarden features](https://github.com/dani-garcia/vaultwarden/wiki#supported-features) · [HTTPS](https://github.com/dani-garcia/vaultwarden/wiki/Enabling-HTTPS) · [Release 1.37.5](https://github.com/dani-garcia/vaultwarden/releases/tag/1.37.5) · [Revocation advisory](https://github.com/dani-garcia/vaultwarden/security/advisories/GHSA-69q9-v8p6-xvx3)

1. **Share.** Invite each Agent as a standard organization User. Create an organization collection for the single shared login. Grant only the intended Agent **View items** on that collection, with password visibility so the fill tool can use it. Keep private items in personal vaults. A moved item becomes organization-owned. [Sharing](https://bitwarden.com/help/sharing/) · [Collection permissions](https://bitwarden.com/help/collection-permissions/) · [Membership](https://bitwarden.com/help/managing-users/) · [Vaultwarden organization implementation](https://github.com/dani-garcia/vaultwarden/blob/1.37.5/src/api/core/organizations.rs)
2. **Sign in.** Reuse an existing session in the Agent’s browser profile when the site permits it. When the site asks for a fresh login, the Agent requests sign-in for a saved login. The proposed service reads the Agent’s Vaultwarden password vault and fills the password and TOTP in the browser. The Agent receives the result and continues. Website challenges that require a person, such as device approval, can still need the Owner. See [password vault restart and idle expiry](#password-vault-restart-and-idle-expiry). [Bitwarden CLI](https://bitwarden.com/help/cli/)
3. **Revoke.** Remove the Agent’s grant on that collection and force an Agent-side sync before relying on the changed access. The server can stop future delivery. A stale local copy, exported value or authenticated website session can still work. For a hard cutoff, also rotate the password, re-enroll TOTP, and revoke website sessions or tokens where supported. Prefer Agent-owned website accounts and site-native delegation where available. [Bitwarden sync](https://bitwarden.com/help/cli/#sync) · [Vaultwarden collection update](https://github.com/dani-garcia/vaultwarden/blob/1.37.5/src/api/core/organizations.rs) · [Collection permissions](https://bitwarden.com/help/collection-permissions/)

## Tradeoffs and Owner decisions

- **Account setup and recovery.** The Owner sets up each Agent’s password vault and decides who can recover it. The Agent handles routine sign-ins. The Owner handles recovery when credentials are revoked or a site requires a person.
- **Sharing scope and response.** Decide which website accounts Agents may use, whether their own TOTP seed may sit with the password, who can rotate a shared login, and which sessions can persist. Origin checking and exact-value redaction keep normal fill values out of conversation. The destination site and same-user code can still access secrets. Browser access does not grant authority to act as the Owner under ADR 0041. [Hermes security and storage](https://github.com/NousResearch/hermes-agent/blob/v0.23.1/website/docs/user-guide/features/credential-vault.md)
- **Hosting and freshness.** Choose the home VM, the patch and restore owner, and the sync policy. `bw` uses cached data during each native fill. Hermes does a full item list for each handle’s metadata, then another CLI call for the value. Sync at an explicit workflow boundary and after grants change. Measure cold and warm timings on the Agent VMs with realistic vault sizes before adding `rbw`, a persistent helper, or per-login forced syncs. [Hermes Bitwarden code](https://github.com/NousResearch/hermes-agent/blob/v0.23.1/agent/vault_backends/bitwarden.py) · [Bitwarden CLI](https://bitwarden.com/help/cli/#sync)

## Password vault restart and idle expiry

Hermes v0.23.1 keeps the Bitwarden unlock token in memory. A restart clears it. Hermes also expires it after 30 minutes without password vault use. The restart test confirmed that direct `bw` unlock works unattended. The private Hermes unlock call completed one synthetic login. Use the documented `bw` commands in a separate login service for the rollout. [Hermes token lifecycle](https://github.com/NousResearch/hermes-agent/blob/v0.23.1/agent/vault_backends/unlock.py) · [Headless vault docs](https://github.com/NousResearch/hermes-agent/blob/v0.23.1/website/docs/user-guide/features/credential-vault.md#headless-sessions) · [Bitwarden CLI unlock](https://bitwarden.com/help/cli/#unlock)

- **Set up once per Agent.** Run the login service under its own Linux service identity with a dedicated `bw` profile. Supply the Agent’s master password as an encrypted service credential, for example through systemd `LoadCredentialEncrypted=`. The service can read that credential at runtime. Keep the credential, CLI profile, session key, and access to the browser’s privileged fill channel outside Agent terminal, file, and code tools. [systemd credentials](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#Credentials)
- **Unlock on demand.** Start the Agent normally. When an authorized login needs a password, the service runs `bw unlock` if its session is missing or expired. Keep the session key in memory and let it expire when idle. Share one unlock attempt across concurrent requests. Fill on the exact saved website origin and return status only. Keep an explicit Owner lock in effect until the Owner restores access. Retry temporary failures within a limit and notify the Owner when the service cannot recover. [Bitwarden CLI unlock](https://bitwarden.com/help/cli/#unlock) · [Hermes origin binding](https://github.com/NousResearch/hermes-agent/blob/v0.23.1/website/docs/user-guide/features/credential-vault.md)
- **Check shared access before use.** Require a successful sync before a fresh login with a shared credential and confirm the item is still available. Pause that login if the check fails. When access must end immediately, rotate the password and TOTP enrollment and revoke existing website sessions where supported. [Bitwarden sync](https://bitwarden.com/help/cli/#sync)

## Verification

### Mac Docker test

**Hands-on scope.** Linux ARM64 Docker on the Mac, Vaultwarden 1.37.5, official `bw` 2026.10.0 and the locally available Hermes v0.22.2 Docker build at `d923a5eb`. The test used temporary CLI data, a disposable Chromium profile attached over loopback CDP, and a Vaultwarden container with a synthetic TLS certificate and an isolated network. All logins and TOTP seeds were generated for the fixture. The comparison uses the newer Hermes v0.23.1 source for supported behavior. [Tested Hermes source](https://github.com/NousResearch/hermes-agent/tree/d923a5eb487a17c0a68801bba9ef0f56c81040a8) · [v0.23.1 release](https://github.com/NousResearch/hermes-agent/releases/tag/v0.23.1) · [Bitwarden CLI release](https://github.com/bitwarden/clients/releases/tag/cli-v2026.10.0)

- **Isolation and sharing passed.** Registered a fixture Owner and two Agents. Created one private item each and granted one organization-owned item via a read-only collection to Agent A. After sync, Agent A saw its private item and the share, while Agent B saw only its own item. Used the Vaultwarden API for grants and the real CLI for reads.
- **Revocation passed after sync.** Removed Agent A’s collection grant. The unsynced CLI could still read its cached password. After `bw sync --force`, the shared item was unavailable to Agent A. Its private item and the Owner’s shared item were retained.
- **Hermes website login passed.** Drove the actual Hermes tool dispatcher with scripted calls, using the genuine `bw` backend and the masked-prompt callback supplied by the fixture. `browser_vault` refused the wrong origin, then filled password and TOTP into the authorized page. The fixture server validated the submitted values. No password, master password, TOTP seed, current code or inherited session-token canary appeared in tool results, including a follow-up DOM value read. A fresh headless Hermes session reported the backend unavailable and refused unlock even when given a valid inherited `BW_SESSION`.
- **CLI throughput.** First Agent login took 7.50 s and cached vault unlock 3.54 s (one run each). Warm process-per-call medians were 3.57 s for password reads, 3.40 s for TOTP and 5.54 s for forced sync (five samples each). Server logs recorded zero requests for the warm reads, and two per forced sync in this run (token refresh and vault fetch).
- **Hermes timings, one run.** Assisted vault unlock took 4.29 s, handle listing 3.28 s, first navigation on the attached Chromium 1.85 s, password fill 6.21 s, and TOTP fill 3.36 s. These are capped, loaded Mac Docker timings for a tiny vault. Those round trips make repeated fresh logins noticeable. Measure on an Agent VM before judging routine speed.

### Hermes v0.23.1 restart test

Used the official Linux ARM64 Hermes v0.23.1 image at `3b421578`, Vaultwarden 1.37.5 and `bw` 2026.10.0. Separate Hermes processes reused the same temporary Hermes and signed-in CLI profiles against a disposable TLS vault. The first process unlocked through the native masked-prompt callback and read the fixture item, then exited. The second process ran the real `browser_vault` dispatcher in the unattended single-query context. [Hermes release](https://github.com/NousResearch/hermes-agent/releases/tag/v0.23.1) · [Headless vault docs](https://github.com/NousResearch/hermes-agent/blob/v0.23.1/website/docs/user-guide/features/credential-vault.md#headless-sessions)

| Path after restart | Observed result |
| --- | --- |
| Stock Hermes with a retained signed-in profile | List reported `unavailable_in_this_session`. Unlock returned `unlock_unavailable`, including with a registered prompt callback. |
| Stock Hermes with inherited `BW_SESSION` or `HERMES_BW_MASTER` | Same refusal. The prior session and a new one from `bw unlock --passwordenv` both read the password and generated valid TOTP directly in `bw`. |
| `bw login --apikey` with a fresh CLI profile | Personal API key authenticated. Vault status stayed `locked` until a separate master-password unlock, after which password and TOTP reads worked. |
| Custom startup code in the Hermes process | Calling the private Bitwarden backend’s `unlock(master_password)` directly made the native handle available. The actual `browser_vault` tools filled password and TOTP in disposable Chromium, and the loopback site accepted the login. Captured tool results omitted both values. |

Stock v0.23.1 offers no supported unattended startup unlock for Vaultwarden. The private call populated the token store in the running Hermes process. This was a prototype. See [password vault restart and idle expiry](#password-vault-restart-and-idle-expiry) for the production recommendation. [Hermes backend](https://github.com/NousResearch/hermes-agent/blob/v0.23.1/agent/vault_backends/bitwarden.py) · [Token store](https://github.com/NousResearch/hermes-agent/blob/v0.23.1/agent/vault_backends/unlock.py) · [Bitwarden CLI unlock](https://bitwarden.com/help/cli/#unlock)

### Stacy pilot

On 2026-11-14, ran a disposable Hermes v0.23.1 profile on Stacy’s x86-64 machine with Vaultwarden 1.37.5 and `bw` 2026.10.0. A scripted call through the Hermes tool dispatcher requested a login from a separate Linux service. The service used `bw unlock --passwordfile` with a fake master password delivered by systemd from a temporary encrypted credential. It filled a password and TOTP in its own disposable Chromium and returned status to Hermes. The local test website confirmed both values. [Hermes release](https://github.com/NousResearch/hermes-agent/releases/tag/v0.23.1) · [Bitwarden CLI unlock](https://bitwarden.com/help/cli/#unlock) · [systemd credentials](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#Credentials)

| Check | Observed result |
| --- | --- |
| Warm login | The service reused its in-memory password vault session. A fresh browser login succeeded. |
| Idle expiry | After the five-second pilot timeout, the same service process discarded the session key. The next login unlocked the Vaultwarden password vault on demand and succeeded. |
| Service restart | Stopped and started the login service and its credential provider. A fresh Hermes process used the retained signed-in `bw` profile and signed in on the first request. |
| Credential access | The Hermes process ran under a different Linux account. It could not read the tested login service and fixture credential paths. Tool replies contained only login and unlock status. |

Both recovery cases ran without an Owner prompt after initial fixture setup. The pilot used a fresh browser for each request. Host reboot, transfer of the website session to the Agent’s usual browser, Bot HQ, live websites, and full secret exposure checks remain unverified. Removed the temporary services, accounts, files, and fake credentials.

## Before production use

1. **Install on one Agent.** Package the login service and Hermes tool. Provision a dedicated Linux identity, `bw` profile, and encrypted service credential. Configure Vaultwarden over HTTPS on the home tailnet and verify backup and restore. Confirm that the service starts after an Agent machine reboot and can unlock after the intended idle timeout without the Owner. Test with fake credentials first.
2. **Prove the Agent can use the session safely.** Run the real Hermes and Bot HQ flow. Verify that the Agent can continue in the authenticated browser after a fresh login. Keep the master password, session key, browser control channel, and raw credential values outside model-callable tools, results, transcripts, and logs. Test against a wrong origin and a representative login form, including any separate TOTP step.
3. **Verify recovery and revocation.** Test concurrent requests, explicit Owner lock, removed sharing grants, failed sync, Vaultwarden outages, and upgrades. Confirm explicit lock stays in force and a revoked shared login cannot start a new session after sync. Verify how the Owner revokes existing website sessions and recovers a lost sign-in.
4. **Start with one Agent-owned website account.** The Owner chooses the account and authorizes first use. Verify a routine sign-in without Owner intervention. Add more accounts after the first Agent can recover from restart and idle expiry and can report exceptions clearly.
