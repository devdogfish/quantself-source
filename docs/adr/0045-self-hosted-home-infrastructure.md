# Quantself runs on the Owner's own machines, with no paid VPS

Status: accepted, 2026-11-11. Amended 2026-11-12: agent placement, Bot HQ and email sending only (ADR 0046). Amended 2026-11-14: Bot HQ runs on `atlas` (ADR 0047). #209 sets the private dashboard hostname and Owner authentication and retains Spaceship DNS. Supersedes the Hostinger VPS deployment described in README.md once the cutover is done.

Quantself, its Agents and its supporting services run on six machines the Owner already owns. The Hostinger VPS is retired. Oracle keeps its existing services and is not part of this system. Nothing here depends on it.

| Machine | Role |
| --- | --- |
| `atlas` (OptiPlex 5060, 64 GB, Proxmox) | The Owner's coding machine and bulk storage: a coding VM for Sandcastle and Codex sessions, Sam Lee's Agent VM, Immich, the Work file space, media apps, LAN DNS and monitoring |
| `keep` (OptiPlex 3040, 16 GB, Proxmox) | The Owner's sensitive data and services: Quantself, the Vault file space, Honcho memory, n8n, and speech-to-text, OCR and redaction |
| `gate` (ThinkCentre M710q) | Gateway for allowlisted public webhooks and Jitsi Meet. Holds no data |
| `stacy`, `tyler` (M710q) | One Agent per physical machine: Stacy Ross and Tyler Scott (ADR 0041) |
| `backup` (M710q, 8 TB USB HDD, Proxmox Backup Server) | Backups only. Only the Owner can log in |

**Trust boundaries.** Sensitive data and services, code that runs untrusted input, Agents, internet-facing services and backups live on different machines or VMs. The coding VM runs arbitrary code (package installs, build scripts), so it lives on `atlas`, away from Quantself, the Vault and Honcho on `keep`. `atlas` still holds the Work space, Immich photos and media, which are less sensitive than the Vault. Sam Lee runs as an 8 GB VM on `atlas` (`vm sam`), growable to 16 GB because LinkedIn outreach keeps a browser busy all day, with its own network, `tag:agent` and no route to other VMs. It is the one exception to one Agent per machine, accepted because no mini is free. The Owner accepts that a VM escape from the coding VM would reach those. The coding VM has its own network with internet access only, holds only the repository, a GitHub deploy key and the Codex login, and has no route to any other VM. Client work runs on rented cloud VMs, never at home. Docker runs inside VMs, never inside LXC. The Owner keeps Proxmox and its kernel updated weekly with automatic security updates, and passes no USB devices or shared folders through to the coding VM.

**Network.** Home has no inbound ports except one forwarded UDP port for Jitsi video. Public webhooks pass through Gate’s method and path allowlist. The #209 cutover candidate uses Gate’s configured Tailscale Funnel hostname and retains existing provider authentication. The private dashboard at `qs.girke.dev` resolves to a Tailscale address. The app maps verified requests from the Owner’s approved Mac and iPhone to the existing Owner account. Agents retain scoped credentials. Retire browser passkeys after both Owner devices, real Agent actions, and live webhook delivery pass. Tailscale tags decide who may reach whom: Agents reach the Quantself API, Honcho and speech/OCR on `keep`; Bot HQ reaches each Agent's Hermes gateway and screen; Quantself does not call Agents; the Proxmox hosts push backups to `backup` with a token that can create backups but not prune or delete them (role permissions to be confirmed in #208), and only the Owner logs in to `backup`; the coding VM (`tag:dev`) reaches the internet (GitHub, package registries) and nothing else.

**DNS.** Spaceship remains the registrar and authoritative DNS provider for `girke.dev`, with its existing delegation and DNSSEC. The staged Cloudflare zone stays inactive and the portfolio apex goes directly to Vercel. Changes to registrar, delegation, Cloudflare activation or apex proxying require explicit Owner approval and an amendment to this ADR. Revisit after both #209 and #278 close if a public self-hosted service needs DDoS protection, WAF or edge caching, or if the Owner wants to consolidate domains behind one DNS API.

Vercel serves the portfolio and provides the public edge. An external proxy reduces its traffic visibility and adds caching and TLS configuration. Tailscale gates private services, and Gate's Funnel handles the allowlisted public webhooks. The existing Spaceship DNS-01 process issues the private dashboard's certificate. Keeping it preserves the verified cutover and keeps the separate #278 mail migration isolated. Cloudflare Registrar would also require a delegation change to Cloudflare nameservers. [Vercel reverse proxy guidance](https://vercel.com/docs/security/reverse-proxy) · [Cloudflare Registrar requirements](https://developers.cloudflare.com/registrar/get-started/transfer-domain-to-cloudflare/)

Use the [girke.dev DNS runbook](../infra/girke-dev-dns.md) to classify hosts, protect the private inventory and verify changes.

**Backups.** Every VM and both file spaces are backed up nightly to the 8 TB HDD, versioned, by Proxmox Backup Server on `backup`. PBS officially wants 4 GiB of RAM plus 1 GiB per TiB stored, which fits the mini's 8 GB. The HDD is a Seagate Expansion desktop drive on USB: a 3.5" disk, likely SMR, so large writes and verify jobs are slow but adequate for nightly backups. It holds backups only and is never served to other machines. Offsite policy amended by the Owner in #254 on 2026-11-14: coordinated Quantself database, original files and the metadata/configuration needed to restore them go nightly to Backblaze B2 Canada East (Toronto), encrypted locally before upload. After an unconstrained tooling comparison and synthetic metadata/growth tests, #254 selected restic through B2’s S3 endpoint: native xattr preservation, bucket/prefix-scoped keys without permanent-version deletion, and a 30-day hidden-version recovery window requiring live verification. This is recoverable version history, not compliance WORM; cloud permissions and version recovery must pass live acceptance. Start with a 10 GB stored-backup target and monitor retained-history growth; modest paid growth is accepted. This replaces the split database-only S3/manual-Proton plan. Future personal-document imports need separate sizing and explicit backup scope; they are not included in the current measured source set. Provider selection is complete; account/credential setup and a verified offsite restore remain #254 work.

**Keep disk encryption.** Reinstall `keep` with Debian 13 on LUKS-encrypted LVM for root, swap and VM storage, then install Proxmox VE. After a power cut, services resume after one Owner unlock over early-boot SSH using Dropbear (#222, #230).

**Restore tests.** Every night `keep` restores the latest `vm quantself` backup into a throwaway 1.5 GB VM with no network, starts Postgres only and checks that it answers, then deletes it. It runs on `keep` so personal data never lands on `atlas`. A failure alerts through Uptime Kuma. One manual full restore is required before anything depends on the backups.

**Standby.** If `keep` is unavailable (a dead SSD or power supply, a bad upgrade, ransomware, a mistaken deletion), the Owner restores its VMs onto `atlas` from `backup`, stops the coding VM, and repoints Tailscale and the tunnel. `atlas` has the RAM for all of them. If `atlas` fails, only coding, Immich and media stop. It is insurance, not an expectation of failure.

**Files.** The Owner keeps documents in two OpenCloud spaces, both organized with Johnny Decimal. **Work** (projects, school, an inbox, footage) runs on `atlas`, on its 1 TB NVMe, and is shared with the Agents: each Agent has its own OpenCloud user who is a member of Work only. **Vault** (finance, identity, health, agreements) runs on `keep` and is owner-only: no Agent has an account on it. Moving a folder between the two changes who can see it. The two spaces share one numbering (no ID exists in both) and split only by whole area: Vault owns the last two areas (80-99) and Work owns the rest, so no area is split across spaces. Each space keeps its own index: Work's lists only Work IDs plus one line naming 80-99 as private, and Vault's lists the Vault IDs. Agents therefore never see Vault folder names. `keep` has a 256 GB SSD, so large files belong in Work.

Quantself does not copy or catalogue either space. It keeps only the files that belong to its own records (inventory photos, audio and attachments, budgeting receipt images), as it does today. Résumés and cover letters are knowledge documents inside Quantself, with sensitive fields handled deterministically by Quantself, so Agents reach them through the scoped API, never through the file spaces.

The Owner opens both spaces from the Mac over Tailscale (a WebDAV mount), so files that are not needed daily stay off the Mac. Desktop, Downloads and current work stay local. Photos and videos go to Immich on `atlas`. OpenCloud was chosen over Nextcloud because the Owner needs file sync only; Quantself owns calendar, tasks and notes.

**Coding.** The coding VM on `atlas` (about 42 GB, reduced from 50 to make room for `vm sam`) runs Sandcastle and Codex sessions: worktrees, `node_modules` and test databases, which keeps that load and disk use off the Owner's Mac. Sandcastle takes one shared ChatGPT login lock, so only one Sandcastle run goes at a time; interactive Codex sessions are not limited. LAN DNS (AdGuard) and Uptime Kuma run in `vm apps` on `atlas`, with the router's secondary DNS set so the internet still resolves if `atlas` is down and healthchecks.io covering "the house is offline".

**Speech, OCR and redaction.** `vm ai` on `keep` (6 GB) runs faster-whisper (small or medium, int8), PaddleOCR and the redaction service that prepares sensitive documents for frontier models (#213). Jobs queue so they take turns. Redacted copies are written to the Work space; originals and the placeholder mappings stay in the Vault. No local LLM is planned: nothing needs one yet, and on a CPU it manages a few tokens per second. Revisit with a GPU or a concrete private job.

**Memory.** Honcho is a VM on `keep`. Its background worker calls a hosted model for now. Local LLMs wait for a GPU.

Accepted costs. `keep` has one small SSD, so Work-sized files stay on `atlas`. The coding VM shares a host with photos and media. When home loses power or internet, the 21:00 Jarvis call, Web Push and meetings stop until it returns. Inbound email is not affected, because the domain's MX forwards it to a normal mailbox outside home (ADR 0040). `keep` is a single machine with a single SSD, so a failure means downtime until a restore onto `atlas`. Jitsi needs a public IPv4 address from the ISP. Behind carrier-grade NAT it needs a small relay server for the video bridge.

Considered: a paid VPS as the public edge (rejected on cost), Tailscale Funnel in place of Cloudflare (needs a `*.ts.net` name and is in beta), Headscale (more to run than it saves), Proxmox clustering (a cluster loses quorum when machines are off), LXC (shares the host kernel and adds a second system to learn), client VMs at home (clients need uptime a home connection cannot promise), a staging VM (the Owner needs only local and production), backups on `keep` or `atlas` (they would share a machine with what they protect, or with untrusted code), plain Debian on `keep` without Proxmox (saves about 2 GB but puts containers on the kernel beside the data), a local LLM VM (no current job needs it; speech, OCR and redaction do not need an LLM).

Clients run on rented cloud VMs billed into each contract, with no client data at home. The two spare 16 GB desktop DIMMs fit none of the current machines. Revisit if a used second OptiPlex is bought for more build capacity.

Setup is tracked in #208 (owner session), #209 (deploy workflow and webhook allowlist) and #213 (redaction service).

**Placement and remote management.** Every machine runs headless and is managed over Tailscale: BIOS set to power on after an outage, Wake-on-LAN where supported, and Proxmox or SSH for everything else. Only power and Ethernet are needed, so the machines can live away from the Owner's room, next to the router or on a switch. Bot HQ's own placement, and how Agents stay up around the clock, are decided at Agent setup (ADR 0046).

## n8n Assistant on Keep

Deployed November 15, 2026. Keep hosts the n8n editor and its PostgreSQL database in VM 2547 (`n8n-keep`). The editor uses Tailscale Serve for the Owner's Mac and iPhone. The sandbox has a separate Ubuntu VM, 2548 (`n8n-sandbox-keep`), with 2 vCPUs, 3 GiB of RAM and a 24 GiB disk. It runs n8n Sandbox Service 1.15.0 with a Sysbox 0.7.1 runner. The sandbox VM and its services start automatically.

The editor and sandbox use the `n8nsandbox` WireGuard interface with one authenticated peer on each end. The editor calls the sandbox API on port 3200 using the sandbox peer address from its private WireGuard configuration. The API binds to that WireGuard address and the guest firewall denies direct LAN requests. The editor uses a key limited to its own sandbox sessions. Mutual TLS protects the separate sandbox API to runner connection. Keep's physical host is shared by both VMs and the sandbox runs inside its own guest.

A check from the actual n8n container reached the API, verified credential enforcement and ran a test command without root access. That test sandbox could not reach the private API address and was removed afterward. The Assistant's own sandbox test passed and the editor opened its chat. GPT-6.1 Sol calls go to OpenAI and optional web search is disabled. On Keep, the deployment journal is `/var/lib/vz/n8n-sandbox-2548/operation.log`. The previous editor Compose file is saved on VM 2547 at `/etc/n8n-sandbox-link/compose.before-sandbox.yaml`.
